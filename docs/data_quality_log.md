# Data-quality log

One row per issue found in the raw data. Nothing gets cleaned, dropped or corrected in the pipeline unless it is in this log with status **agreed**.

**How to add an issue**
1. Give it the next ID (DQ-xx) and fill in every column. Write "?" if you don't know yet.
2. **Evidence** must point to something others can rerun: a notebook and section, or a short code snippet.
3. Leave **Decision** and **Status** empty until the team has discussed it.
4. When the fix is in the code, set the status to **implemented** and name the script.

**Columns**

| Column | What to write |
|---|---|
| ID | DQ-01, DQ-02, ... |
| Signal(s) | Short names from `data/processed/signals.csv` (e.g. `shaft_kw`) |
| Period | From – to (UTC), or "all year" |
| Type | One of: missing / gap · stuck or placeholder value · out of range · sign or unit · drift or bias · duplicate · timestamp · other |
| What we see | One or two sentences, with numbers (how many readings, how big) |
| Evidence | Notebook + section, or a code snippet |
| Readings affected | Count, and % of that signal |
| Impact | What breaks if we ignore it (e.g. "power 20% too low after Jul → looks like fouling") |
| Options | Keep · flag only · set to NaN · correct (how) · drop rows · use other signal |
| Decision | Filled in at the team meeting |
| Status | open · agreed · implemented (script) · rejected |
| Found by / date | Initials, date |

## Notes

**Cleaning and steady-state filter (1 Nov, `make_10min.py`, `data_cleaning/readings.py`, `prepare_features.py`).** Each step was added on its own and the two models rerun. Spread = robust residual spread of the expected-power fit in the reference period. MAPE = speed baseline, week-based folds.

| Step | Steady rows | Spread | MAPE | Aug / Sep fouling (laden) |
|---|---|---:|---:|---|
| Before | 27,966 | 7.9 % | 2.39 % | 19.9 / 25.1 % |
| + circular wind angle, noon check | 28,032 | 7.7 % | 2.46 % | 17.3 / 23.6 % |
| + limits, stuck SOG | 27,773 | 7.8 % | 2.47 % | 16.6 / 22.1 % |
| + slope test on top of the spread rule (**used**) | 24,825 | 7.6 % | 2.30 % | 17.0 / 23.0 % |
| Slope test instead of the spread rule (rejected) | 28,637 | 9.5 % | 4.81 % | not used |
| Limits, stuck SOG and spike removal (rejected) | 27,885 | 7.8 % | 2.47 % | not used |

- Slope test: Dalheim & Steen (2020), t-test on the slope in moving windows, α = 1 %, engine rpm over 5 min and heading over 20 min. A block counts if at least 90 % of it passes. Engine rpm is used because shaft rpm comes from the faulty torquemeter.
- Used alone it fits much worse. It only asks whether rpm and heading drift, so blocks with unsteady speed pass. Any stricter filter lowers the spread, so the small gain comes at the cost of 11 % of the steady rows.
- Spike removal (5 standard deviations from a 5-min rolling median, runs up to 1 minute) did not improve the fit, and the virtual power holdout got worse (1.0 % → 1.2 %), so it was left out.
- The wind fix lowers Aug–Sep by about 2 points: those values were partly a wind error.
- Reading limits removed 51 readings and the stuck rule 13,603 (57 h). The draft limit was raised from 14.5 to 16 m: aft draft reaches 15.5 m when laden and trimmed by the stern.
- Correlation matrix: compare the two periods with care. After July power covers a much wider range (about 2–5.5 MW), which pushes correlations up. Power vs speed is 0.00 before July only because laden and ballast are mixed: within laden it is −0.51 and within ballast +0.77.

**Power fix for DQ-02, DQ-14 and DQ-18 (28 Oct, `prepare_features.py`).** Implemented on branch `fix/scavenge-power` and waiting for team OK. Power after 10 Jul, and wherever the torquemeter reads 0 while the engine turns, now comes from **scavenge air pressure + engine rpm** instead of fuel flow + rpm. Neither the torquemeter nor the fuel meter is involved. Both models are fitted on Jan–Apr and tested on 1 May – 9 Jul (torquemeter trusted), steady rows only:

| Virtual power from | Holdout MAPE | Torquemeter ÷ estimate, Jul–Sep | Oct–Dec |
|---|---|---|---|
| Scavenge pressure + engine rpm (now used) | 1.0 % | 0.81–0.83 | 0.76–0.79 |
| Fuel flow + engine rpm (before) | 5.0 % | 0.76–0.84 | 0.66–0.69 |

- The torquemeter ratio against the scavenge estimate is flat within each period and steps at 10 Jul and mid Oct. That fits a sensor scale fault (DQ-02); fouling can't change power at a given air pressure. Against turbocharger-based power (`04_noon_reports.ipynb` §3b) the torquemeter reads 0.76 (Jul–Sep) and 0.77 (Oct–Dec), so the second step is not clear: scavenge-based power reads about 4 % low in Jul–Sep at higher loads. Summary: the torquemeter reads about 18–24 % low from July depending on the reference signal, and about 23 % from mid Oct.
- The fuel-based estimate reads about 16 % above the scavenge estimate from Oct to Dec (median of steady rows), which confirms DQ-18. Fuel-based power was turning that drift into fake fouling: the monthly fouling indicator drops from 50 → 31 % (Oct, ballast), 40 → 23 % (Nov, ballast) and 17 → 3 % (Dec, laden). (The figure `fouling_before_after.png` was removed on 28 Oct: it was made before the speed fix and no script in the repo produces it. `plots4report/fouling_trend.png`, made by `submission.py`, shows the current result.)
- DQ-14 dropouts are now NaN in `power_meas_kw`, and engine rpm replaces shaft rpm there. This adds 1,769 steady rows in the reference period (mostly June).
- Noon-report fuel only partly supports DQ-18: meter ÷ noon fuel is 1.24 in Nov, but 1.08 in Dec and 0.99 in Oct. Update: noon fuel follows the meter all year, so it is most likely read from the meter and is not an independent check (DQ-29).
- Limitation: the pressure–power relation can drift with turbocharger fouling or air temperature. The flat torquemeter ratio within each period suggests it doesn't here.

**Ballast excess in Oct–Nov (28 Oct, `plots4report/ballast_oct_dec_check.png`).** After the power fix, ballast still reads +31 % (Oct) and +23 % (Nov) while laden Dec reads +3 %. After the speed fix of the same day these became +25 % (Oct) and +11 % (Nov), laden Dec +4 %; the figure was made before the speed fix and is not produced by a script in the repo. Checked against the reference ballast rows (clean, steady):

- Not the power estimate: in the reference period, scavenge-based power matches the torquemeter to +0.0 % in the 3.0–3.5 MW ballast band where Oct–Nov sails (2,075 rows).
- Not loading: Oct–Nov ballast is slightly lighter than the reference (34.8k vs 35.9k t), which would make the ship faster.
- At equal power the ship is slower: 10.51 vs 11.25 kn at 3.0–3.5 MW (−0.74 kn, −6.6 %, about +20 % power at P ∝ V³). GPS speed alone shows the same drop, so it is not the current model. Panel A.
- Compare at equal power, not equal speed. The ship runs at almost fixed power settings and speed scatters ±1.5 kn around them, so binning by speed flattens any change (panel B). For the same reason, adding speed to the baseline correction overfits (fitted P ∝ V¹, and laden Aug–Dec drops to −20 %).
- The propeller law does not confirm it: power at the same engine rpm is unchanged (about +1 %, panel C), while 20 % more resistance should make the propeller run heavier.
- Plausible cause: noon reports show about 11 port days at 27 °C between 25 Sep and 10 Oct (inside the DQ-08 gap), just before the high readings.
- Weak points: the only reference ballast at this power is one April voyage, so a route or current difference can't be ruled out. Laden Dec (59k t) has no laden reference near its displacement and rests on the towing-curve interpolation; a cleaning during the Nov stops (196 h) would also explain it, but only the cleaning-events file can tell.
- For the report: quote Oct–Nov ballast as about 0.7 kn speed loss (about 20 % power) against the April voyage, not confirmed by the propeller law, rather than the monthly medians (now +25 % Oct, +11 % Nov).
